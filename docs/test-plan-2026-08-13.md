## Description des tests

**Automatisés** — `tools/acceptance.py` (USB seul, ~2 min/unité) :

| Test | But (exigence) | Méthode | Critère PASS |
|---|---|---|---|
| **V1** boot & console | l'unité démarre et reste stable | STATUS ×3 sur ~15 s | uptime monotone, serial stable, pas de reboot |
| **V13** identité / révision HW | traçabilité + détection révision (MAX7319) | lecture STATUS | serial + fw + hwrev présents et cohérents |
| **V6** IMU | capteur d'inclinaison sain | STREAM ON, mesure du vecteur g | \|g\| ≈ 1 (0,8–1,2) + trames reçues |
| **CFG** config | config par USB fiable (usage normal) | CONFIG SET puis GET (survey_id) | relu = écrit, restauré |
| **V11** batterie | jauge plausible | STATUS battery | valeur 2–100 % *(WARN si lit `1` = bug FW connu)* |
| **V7** transfert données | **récupération USB fiable** (usage produit clé) | GET tout un survey (record ARRÊTÉ), parse, compte corruption + détecte freeze | 0 record corrompu, pas de freeze *(WARN < 10 %, FAIL ≥ 10 % ou freeze)* |
| **V2** ADC ×3 | 3 voies géophone acquièrent | sur les `.dat` transférés : voies présentes, non figées, non saturées | 3 voies vivantes *(WARN si saturé, FAIL si voie manquante/figée)* |
| **V8** miniSEED | format de sortie valide | parse des `.dat` (simplemseed v3) | fichiers lisibles / bien formés |

**Manuels** — à faire à l'œil, par unité :

| Test | But | Méthode | Critère PASS |
|---|---|---|---|
| **V9** USB-MSD | exposition des données | brancher l'USB | le disque de masse monte, fichiers visibles |
| **V10** LEDs WS2812 | indication d'état | observer aux transitions | les 4 LEDs répondent (boot / fix GPS / record) |
| **V15** acquisition réelle | l'unité fait son métier | **bouton** → record → stop → relancer `acceptance.py` | nouveau survey valide : 3 voies, horodaté GPS |

**Reportés (PAS aujourd'hui)** : V3 synchro inter-voies, V5 dérive horloge, V14 watchdog
(banc/instrumentation dédiés) ; corrélation temporelle TIME-05 (précision à régler) ;
calibration fine sensibilité/f0/ζ ; V12 BLE (N/A sur V2/V3.0).

## Bloc 0 — Flash uniforme des 9 (PRÉALABLE) (~45 min)

Les 9 doivent tourner le **MÊME** firmware pour que la comparaison soit valide.
Constaté : CG0-000009 = `0.1.0.211/dae370c+`, CG0-000006 = `0.1.0.205/fc244d8` (6
commits en retard, **sans le fix GET** → V7 fausserait).

**Firmware cible : build test-bench `0.1.0.211 / dae370c+`** = `build/zephyr/zephyr.hex`
du 2026-08-11 (config test-bench confirmée : `CDC_LARGE_TX`, `ALLOW_ACQUISITION_ON_USB`,
`USB_MASS_STORAGE` off ; GET fix + START/STOP idempotent). C'est le firmware déjà sur
CG0-000009. *(Rebuild propre `b90268b` possible EN WSL — `./scripts/build.sh -n geophone
--clean -e test-bench.conf` — mais PAS depuis Git Bash : mount Docker cassé.)*

**Flash par USB DFU** (validé sur CG0-000006 — pas de STLink → évite le risque de
séquençage d'alim, cf. incident STLink) :
```powershell
$cli = "C:\Program Files\STMicroelectronics\STM32Cube\STM32CubeProgrammer\bin\STM32_Programmer_CLI.exe"
$hex = "C:\Projets\geophones-firmware\build\zephyr\zephyr.hex"
# 1) mettre l'unité en DFU (BOOT0 + reset) — vérifier : "STM32 Bootloader" dans les périphériques
& $cli -l usb                           # confirme le device DFU (USB1)
& $cli -c port=USB1 -w $hex -v          # flash + vérifie
& $cli -c port=USB1 -g 0x08000000       # démarre l'app (le -rst SWD ne marche pas en DFU)
```

**Vérif après flash** : `STATUS?` doit renvoyer `fw: 0.1.0.211`, `git: dae370c+` sur les 9
(= ce que V13 contrôle). Le serial survit au DFU. Re-flasher aussi CG0-000009 (déjà OK) au besoin.

**État** : ✅ CG0-000009 (déjà), ✅ CG0-000006 (flashé) ; reste 7 unités.

## Bloc A — Acceptation automatisée des 9 (~1 h 30)

Prérequis : GUI fermé, python du venv. Boucle **par unité** :

1. Brancher l'unité en USB.
2. **Enregistrer ~30 s ambiant au BOUTON** (record réel, faible amplitude) → stop
   bouton. → donne un V2/V7 propre. *(sauter si l'unité a déjà un bon survey.)*
3. Lancer :
   ```
   .\venv\Scripts\python.exe tools\acceptance.py
   ```
4. Noter le verdict `>>> <serial> : PASS/WARN/FAIL <<<` dans le tableau ci-dessous.
5. Si le board gèle (rare en défaut) : reset + relance (données sûres sur SD).

Puis agréger :
```
.\venv\Scripts\python.exe tools\acceptance.py --fleet
```

## Bloc B — Checklist manuelle (par unité, en parallèle) (~30 min)

Pour CHAQUE unité (voir tableau) :
- **V9 USB-MSD** : le disque de masse monte, fichiers visibles.
- **V10 LEDs** : réponse aux états (boot / fix GPS / record).
- **V15 record réel** : bouton → enregistre (LED) → stop → `acceptance.py` redonne V2/V7 PASS.

## Bloc C — Triage (~30 min)

- Lire `--fleet`. Pour chaque **FAIL / WARN**, catégoriser :
  - **défaut d'UNE unité** (rework HW ponctuel) vs **SYSTÉMATIQUE** (défaut design/firmware).
- Métriques transversales à relever :
  - **taux de corruption transfert** par unité (V7) — combien > 2 % ?
  - **fréquence du bug `battery=1`** (V11) — combien d'unités touchées ?
  - **gels** (au START-USB test-only, ou ailleurs ?).

## Bloc D — Synthèse go/no-go (~30 min)

Rubrique de décision (pour vendredi) :
- **GO** si les 9 sont **PASS ou WARN** sur V1/V13/V6/CFG/V11/V7/V2/V8 (boot, identité,
  IMU, config, transfert fiable, 3 ADC présents, miniSEED valide).
- **NO-GO / conditionnel** si **FAIL systématique** (même défaut sur plusieurs unités) :
  voie ADC manquante/figée, transfert ≥ 10 % corrompu ou freeze hors START-USB, miniSEED illisible.
- Rédiger le résumé : critères design validés, défauts (unité vs design), verdict.

## Unités particulières / exclusions

- **CG0-000008 — BOARD MODIFIÉ, exclu de la flotte production.** Résistances
  d'entrée ADC retirées (mod caractérisation : impédance 1 MΩ de l'ADS1285). En
  enregistrement, **LED D13 (pixel Health) rouge = `HealthStatus::STATUS_RUNTIME_ERROR`**
  après quelques secondes → enregistrement stoppé. Cause la plus plausible : entrées
  ADC haute-impédance/flottantes → faute ADS1285/gatherer d'acquisition (conséquence
  de la MOD, **pas un défaut de production**). Batterie mesurée **pleine 7,57 V** mais
  jauge lit 2 (= bug de jauge général, coïncident). Pour un verdict valide : remettre
  les résistances (config prod) OU garder exclu. Log console USART3 confirmerait le
  sous-système exact. Firmware flashé OK (`0.1.0.211/dae370c+`).
